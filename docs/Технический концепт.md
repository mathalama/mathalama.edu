## Технический концепт: «Событийный конвейер обучения» (Event-Driven LMS)

Основная идея в том, что любое действие на платформе — это **событие (Event)**, которое публикуется в очередь, а другие сервисы независимо на него реагируют. Это разгружает основное API и делает систему готовой к высоким нагрузкам.

### 1. Архитектурный стек (Рекомендованный для ЕС)

- **Backend:** Go (Golang) — чрезвычайно популярен в Европе для бэкенда благодаря производительности.
    
- **База данных:** PostgreSQL (основные данные) + Redis (для кэширования профилей и сессий).
    
- **Брокер сообщений:** NATS JetStream или RabbitMQ (для асинхронных задач).
    
- **Хранилище:** MinIO (локальный аналог AWS S3 для хранения файлов домашних заданий и видео-уроков).
    

## 3 ключевые «киллер-фичи» для твоего портфолио

Интервьюеры в Европе любят, когда кандидат умеет решать сложные технические проблемы. Вот три фичи, которые нужно реализовать и описать в резюме:

### Фича №1: Асинхронный движок автоматизации доступа (Content Dripping Engine)

- **Проблема:** Когда куратор принимает домашнее задание, система должна: открыть следующий урок, пересчитать прогресс студента, проверить, не завершил ли он весь модуль, и отправить уведомление. Если делать это в одном HTTP-запросе, бэкенд будет тормозить, а при ошибке отправки email вся трансляция в БД упадет.
    
- **Решение:** Куратор жмет кнопку «Одобрить» $\rightarrow$ API мгновенно пишет статус Approved в базу и бросает событие submission.approved в брокер (NATS/RabbitMQ). API сразу возвращает куратору HTTP 200.
    
- В бэкграунде запускаются независимые **воркеры (Workers)**:
    
    - _Worker 1_ ловит событие и открывает доступ к следующему уроку в БД.
        
    - _Worker 2_ отправляет Email/Slack уведомление студенту.
        
    - _Worker 3_ обновляет аналитический дашборд группы.
        
    - _Результат:_ Идеальный отклик интерфейса и изоляция ошибок (если упадет почтовый сервер, уроки все равно откроются).
        

### Фича №2: GDPR-Compliance Worker (Анонимизация по стандарту ЕС)

- **Проблема:** В Европе за нарушение GDPR (хранение данных удалившихся пользователей) можно получить огромный штраф. Но если просто удалить строку пользователя из БД, сломается статистика курсов (база не поймет, чьи домашние задания лежат в истории).
    
- **Решение:** Реализация паттерна **Soft Delete + Anonymization Pipeline**. При запросе на удаление аккаунта, воркер:
    
    1. Генерирует криптографический хэш вместо реального email.
        
    2. Заменяет first_name и last_name на случайную строку (например, Student_#8492).
        
    3. Отправляет запрос в S3-хранилище на физическое удаление всех файлов (аватарок, архивов с ДЗ), которые загружал этот пользователь.
        
    4. Оставляет саму запись в БД для аналитики, но идентифицировать человека по ней больше невозможно.
        

### Фича №3: Интеграция концепции Observability (Метрики и Логи)

- **Проблема:** Тимлиды в Европе часто жалуются, что джуны/мидлы умеют писать код, но не умеют поддерживать его в продакшене.
    
- **Решение:** Твое приложение должно отдавать структурированные JSON-логи и метрики.
    
    - Настрой сбор метрик через **Prometheus**: сколько запросов проходит в секунду, сколько времени занимает обработка ДЗ куратором, есть ли задержки в очереди сообщений.
        
    - Выведи это на красивый дашборд в **Grafana**. Достаточно сделать один скриншот этой Grafana для README.md в GitHub, чтобы твое резюме автоматически поднялось выше большинства конкурентов.
        

## Почему эта идея «продаст» тебя на собеседовании?

На собеседовании ты будешь рассказывать не о том, как ты сделал формочки для GetCourse, а о том:

1. Как ты спроектировал **Event-Driven систему**, устойчивую к пиковым нагрузкам (например, когда 500 студентов одновременно сдают дедлайн).
    
2. Как ты решил проблему консистентности данных при асинхронной работе.
    
3. Как ты учел жесткие **юридические требования рынка (GDPR)** на уровне архитектуры БД.
