## Технический концепт: Событийный конвейер обучения (Event-Driven LMS)

Основная идея архитектуры платформы заключается в том, что любое действие пользователя — это **событие (Event)**, которое публикуется в очередь, а другие сервисы независимо на него реагируют. Это существенно разгружает основное API и делает систему готовой к высоким нагрузкам.

### 1. Архитектурный стек

*   **Backend:** Go (Golang) — выбран благодаря высокой производительности, минимальному потреблению ресурсов и отличной поддержке конкурентности из коробки.
*   **База данных:** PostgreSQL (хранение реляционных структурированных данных) + Redis (для кэширования профилей, сессий и хранения FSM-состояний Telegram-бота).
*   **Брокер сообщений:** NATS JetStream (асинхронная гарантированная доставка событий с поддержкой балансировки потребителей через Queue Groups).
*   **Хранилище:** MinIO (локальное объектное хранилище S3 для хранения медиафайлов, видеоуроков и загружаемых студентами PDF-конспектов).

## 2. Ключевые технические решения

### Асинхронный движок автоматизации доступа (Content Dripping Engine)
*   **Проблема:** При проверке и одобрении домашнего задания куратором система должна выполнить цепочку действий: изменить статус проверки, открыть следующий урок, пересчитать прогресс студента, проверить завершение модуля и отправить уведомление. Синхронное выполнение этой цепочки в рамках одного HTTP-запроса приводит к задержкам ответа API, а сбой в отправке почты отменит всю SQL-транзакцию.
*   **Решение:** API-сервер куратора мгновенно обновляет статус сдачи в БД на `approved`, публикует событие `submission.approved` в NATS JetStream и сразу же возвращает ответ HTTP 200 OK.
*   **Асинхронные обработчики:** В фоновом режиме запускаются независимые воркеры (Workers):
    *   *Dripping Worker* перехватывает событие и разблокирует доступ к следующему уроку в БД.
    *   *Notification Worker* формирует и отправляет Email/Telegram уведомление студенту.
    *   *Analytics Worker* обновляет общие показатели успеваемости когорты.

### Конвейер анонимизации данных (GDPR Compliance Pipeline)
*   **Проблема:** Требование регламента GDPR «Право на забвение» обязывает полностью удалять персональные данные (PII) пользователя по запросу. Однако простое физическое удаление строки (`DELETE`) из таблицы пользователей приводит к нарушению целостности данных и ломает историческую статистику прохождения курсов.
*   **Решение:** Реализация паттерна **Soft Delete + Anonymization Pipeline**. При запросе на удаление аккаунта:
    1.  Запускается двухфазный процесс. Учетная запись переводится в статус `deleted_scheduled` на 14 дней.
    2.  По истечении 14 дней фоновый воркер запускает анонимизацию: хэширует email-адрес алгоритмом SHA-256 с солью, стирает ФИО пользователя и сбрасывает привязки Telegram.
    3.  В S3-хранилище отправляется запрос на физическое удаление всех файлов (PDF-конспектов, аватарок), загруженных пользователем.
    4.  Аналитические метрики в СУБД остаются нетронутыми, но идентифицировать реального человека по этим записям становится невозможно.

### Наблюдаемость распределенной системы (Observability)
*   **Проблема:** В микросервисной среде со множеством асинхронных процессов сложно отлаживать сбои и контролировать производительность бэкенда.
*   **Решение:** Интеграция средств Observability с первых этапов проектирования:
    *   **Структурированное логирование:** Все сервисы пишут логи в формате JSON с обязательным полем `correlation_id` для сквозного отслеживания цепочки событий.
    *   **Метрики:** Экспорт Prometheus-метрик (количество обработанных событий в секунду, время отклика gRPC, задержки в очередях NATS).
    *   **Визуализация:** Дашборды в Grafana для мониторинга здоровья инфраструктуры в реальном времени.

## 3. Цели проектирования системы

1.  **Масштабируемость:** Способность выдерживать пиковые нагрузки в периоды дедлайнов сдачи домашних заданий без деградации времени отклика интерфейса.
2.  **Отказоустойчивость:** Изоляция сбоев внешних интеграций (например, почтового сервера) от ядра системы благодаря асинхронным очередям сообщений.
3.  **Юридическая и техническая безопасность:** Соблюдение стандартов защиты данных (GDPR) на самом фундаментальном уровне проектирования базы данных и хранилища файлов.
